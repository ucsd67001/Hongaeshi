# 本返し（Hongaeshi）

> 読んだあとに、ありがとうを。

読み終わったあとに、その本を支えた人（著者・出版社・独立系書店）へ気持ちを返す場所。

**いまは架空のポイントで動かすトライアル段階。実際のお金は1円も動かない。**

- 本番: https://hongaeshi.web.app
- Firebase プロジェクト: `hongaeshi`
- ダミーデータのデモ（ログイン不要・単一HTML）: https://hongaeshi.web.app/demo

---

## なぜ作っているか

本を買う以外に、本の世界へお金を返す導線がない。図書館で借りた本、古本で買った本、
昔もらった本 ― 読んで確かに何かをもらったのに、その感謝が著者にも出版社にも書店にも
届かないまま終わる。そこを埋めたい。

ユーザー側の動機は「出版業界を救う」ではなく、もっと個人的なもの。だからキャッチコピーは
**「読んだあとに、ありがとうを。」**で通す。

### いまユーザーにとっての価値（2026-09-23 の見立て）

ポイントは架空で配られたものなので、「返す」こと自体の重みはまだ小さい。
いま届いている価値は、**どの本・著者・出版社が推されているか、
推している熱心な読書家が誰か、が見えること。**
だから次に作るのは「推し」を見えるようにするもの（下の「次に作るもの」）。

### トライアルで見たいこと

本物のお金ではないので、**「いくら払うか」は測れない。**測れるのは次の3つ。

1. 配られたポイントを、そもそも使うか
2. どの本に使うか（新刊か、昔読んだ本か、絶版か）
3. **ことばを書くか**（金額だけ送る人と、書く人の比率）

とくに3つめ。購買データでは絶対に取れないのが読後の感情で、
それが出版社・書店にとっての価値になる、というのがこのサービスの賭けどころ。

## 作りの要点（ここだけは先に読んでほしい）

### Cloud Functions は「知らせる」「読んで返す」ためだけ（書き込みには使わない）

> 2026-09-23 に Blaze（従量）へ切り替えた。ただし**下の作りは変えていない。**
> Functions で書き込むと、書き込みの筋道が2本になって、
> ルールで縛れる範囲の外に集計が出ていく。無料枠のためではなく、作りとして避けている。
>
> ⚠️ 2026-09-24 に `functions/` を足したが、**運営へのメール通知だけ**で、Firestore には何も書かない
> （上の理由に当たらないので可、と決めた）。
> 2026-09-26 に「**読んで、答えを返すだけ**」の処理（いまの気分で選ぶ）も可に広げた。
> **ここから Firestore に書く処理を足さないこと。**

受取人の受取額も本ごとの集計も、**サーバー側で足し込むカウンタを持たない。**
必要なときに `returns` を集計クエリで数える。だから書き込みは
「自分の財布を減らす」＋「返しを1件つくる」の2つだけで済み、無料枠のまま走る。

そのかわり、**この2つが釣り合っていること**を `firestore.rules` の `getAfter()` で縛る。

> ⚠️ アプリ側は財布の更新と返しの作成を**必ず1つの writeBatch で**送ること。
> 別々に送ると必ず弾かれる（`public/共通.js` の `本返しする()`）。

### Firestore の中だけ、名前が ASCII

⚠️ **セキュリティルールの言語は、識別子に日本語を受け付けない**（コレクション名・
フィールド名・関数名。書くと `token recognition error` でデプロイが落ちる。コメントは通る）。
そのため Firestore の中だけ ASCII にして、`public/共通.js` が読み書きの境目で読み替えている。

| 画面での呼び名 | Firestore | 主な項目 |
|---|---|---|
| 財布 | `wallets` | `balance` / `granted` / `created` |
| 返し | `returns` | `book` / `from` / `anon` / `amount` / `parts` / `toIds` / `text` / `at` |
| 残し | `keeps` | `book` / `from` / `pledge` / `text` / `at` |
| 本 | `books` | `isbn` / `title` / `authorText` / `publisherText` / `year` / `pages` / `cover` / `amazonLinks` / `to[]` |
| 主体 | `entities` | `type` / `name` / `key` / `aliases` / `claimed` / `claimedBy` |
| 名乗り | `users` | `name` / `mark` / `color` / `photo` / `profilePublic` / `updatedAt`　⚠️ 表示名はここだけ。記録に焼き付けない |
| 申請 | `requests` | `title` / `author` / `publisher` / `isbn` / `memo` / `done` |
| 管理者 | `admins` | uid があれば管理者。**画面からは書けない** |

Firestore から読んだものは `共通.js` の中で必ず日本語のかたちに直してから返す。

### 主体（著者・出版社・書店）は1つのコレクション

`entities` に `type` で混ぜてある。分けなかった理由：

- **返しの宛先が1つのキースペースで済む。**分けると `parts[].to` に型が必要になり、
  結局は合成キーで1つの名前空間に戻すことになる
- **型は後から変わる。**個人経営の古書店は人でもあり店でもある。翻訳者・装丁家を
  足すたびにコレクションを増やしたくない

**IDは型込みの正規化キー**（`author:立花隆` / `publisher:文芸春秋`）。
「あれば取得、無ければ作成」が検索なしで冪等にできる。

### 名寄せの規則は `public/名寄せ.js` にしかない

⚠️ ブラウザ（管理画面からの登録）と手元の道具の**両方から読む。**
同じ規則を2か所に書くと、片方で作ったIDともう片方で作ったIDが食い違って、
**同じ相手が2つの主体に割れる。**

実際に起きたこと：`文藝春秋`（旧字）と `文芸春秋`（新字）が別の主体になった。
NFKC では統合されないので、照合キーだけ新字に寄せている。

**機械で寄せられないもの**（`Ende,Michael` と `ミヒャエル・エンデ` のような
ローマ字と日本語表記）は、管理画面の**統合**機能で人が繋ぐ。
管理画面でいちばん重要なのは編集や削除ではなく、この統合。

#### 名寄せには3種類の関数がある。混ぜないこと

| | 用途 | 例 |
|---|---|---|
| `出版社キー` / `著者キー` | **同じ相手か**の判定。IDになる | 文藝春秋 → `文芸春秋` |
| `名前をととのえる` | **画面に出す名称**の整形 | `ハンス・フィッシャ－` → `ハンス・フィッシャー` |
| `ゆるいキー` | **統合の候補さがしだけ** | 記号も長音符も全部落として比べる |

⚠️ `ゆるいキー` は**照合に使わない。**別人を同じに見せるので、
自動で統合すると同姓同名を潰す。記録は消せないので取り返しがつかない。

⚠️ `名前をととのえる` は **`読める名に` の内側で必ず呼ばれる。**
呼ぶ側それぞれで整形すると、新しい道具を足したときに忘れる
（実際に末尾に空白のある「角川グループパブリッシング 」ができた）。

#### 機械には絶対に分からないもの

- **会社の合併・改称**（KADOKAWA ／ 角川書店 ／ 角川グループパブリッシング）
- **2人が1つの名前になっているもの**（`Ado 小松成美` — Adoが語り手、小松成美が書き手）
- **翻訳者と著者の区別**（書誌の著者欄は両者を区別しない）

点検の道具はこれらを**候補として挙げるだけ**。決めるのは人。

```bash
node 04_tools/名寄せを点検.mjs               # ①名称の乱れ ②同じかも ③2人が1人
node 04_tools/名寄せを点検.mjs --ととのえる   # ①だけ自動で直す
node 04_tools/名寄せを点検.mjs --統合 <残すid> <消すid>…
```

### 権限は3段

| | |
|---|---|
| ① 管理者 | `admins` に uid があるひと |
| ② 受取人 | 自分が引き継いだ（`claimedBy` が自分の）主体を持つひと |
| ③ 利用者 | 入っているだけのひと |

②のために新しいコレクションは作らない。`entities` の `claimed` / `claimedBy` で表せる。

⚠️ `admins` は**ルールで書き込み禁止**。増やせるのは Admin SDK からだけ
（画面から増やせると「管理者が自分で管理者を作れる」入口になる）。

### 表示名は記録に焼き付けない

⚠️⚠️ 表示名は `users/{uid}` にだけ持ち、画面で引く。**`returns` / `keeps` に名前を保存しない。**

記録は書き換えない決まり（`allow update: if false`）なので、焼き付けると
**あとから名前を変えても過去の分に本名が残る。**
「Googleの本名を出したくない」と気づくのは、たいてい1回投稿した後。

名乗りを決めていない人は、Googleの表示名をその場で使うだけで、保存しない。
決めた人だけ `users` に入る。帯の自分の名前 → マイページ（`/me`）→「名前・しるし・公開を変える」で設定の窓を開く
（2026-09-24 に、設定の窓・わたしの本返し・読書家のページへの入口をマイページに集めた）。

⚠️ **`users/{uid}` は、入っただけではできない。**設定の窓で「これにする」を押したときに初めてできる。
前は窓を自分で開くまで作られず、2026-09-26 の時点でログインした4人のうち3人が名前を決めていなかった
（本人の画面では Google の名前、**ほかの人の画面では「読者」**。読書家のページも公開できない）。
→ **まだ名前を決めていない人が入ったら「はじめに、名前を決めてください」の窓を出す**（2026-09-26 決定：A。
`app.js` の `名前を決めてもらう`）。1つのタブで1度だけ（閉じた人に何度も出さない）。
- ⚠️⚠️ **名前の欄に Google の名前を入れておかない。**入れておくと「これにする」を押しただけで本名が出る。
  しるしの字も同じ理由で入れない（前は Google の名前の1字目だった）
- ログインした時点で Google の名前で `users` を作る案（B）は、本人が気づかないうちに本名が出るので見送った
- `users` が読めなかったとき（`名乗りを読めた` が false）は出さない。決めてある人に出してしまうため

#### しるし（顔と印）

名前が出るところには、必ず**しるし**が付く（声・番付・受取人の控え・帯）。
`public/app.js` の `名と印()` と `しるし()` を通すこと。素の名前を直接書かない。

- **顔**：Storage の `icons/{uid}` に置いた画像。**192px 四方の WebP に縮めてから上げる**
  （`共通.js` の `顔をあげる`）。原寸で置くと、声が並ぶ画面で毎回それを読みに行く
- **印**：1文字＋色。画像を上げていない人に出る。外への読み込みが無く、壊れない。
  Googleの顔写真を出したくない人は、これで済ませられる

⚠️ `photo` に入れてよいのは Storage のURLだけ（ルールで縛っている）。
好きなURLを入れられると、誰でも見られる画面が他所のサーバへの発信元になる。

⚠️⚠️ **匿名で送った分には、しるしも uid も出さない。**
`返しを直す` は匿名なら `送り主` を `null` にする。
uid を画面まで持っていくと、匿名の行に誰が書いたかが載る。

⚠️ ルールの字句解析は、**文字列の中でも `//` をコメントとして読む。**
`'^https://…'` と書くとそこから先が消えてデプロイが落ちるので、`[/][/]` と書く。

### 未ログインでも棚は見える

本・主体・返し・残し（声と集計）は公開読み取り。認証が要るのは
**本返し・復刊を願う・ことばの記録、マイページ、受取人の控え、登録の申請、訂正の連絡**だけ。
リンクを共有されたときに入口しか見えないのは、参加してもらう上で損なので。

⚠️ 集計を読む画面は、**入っているかどうかで分けない。**本の一覧だけ古い作りが残っていて、
未ログインだと「返された分」の並べ替えが全冊 0pt になっていた（2026-09-23 に直した）。

### ポイントの配り方

| | |
|---|---|
| はじめて入ったとき | 10,000pt |
| 毎月 | 3,000pt |
| 1回に返せる額 | 100〜50,000pt |
| 受取人に渡る割合 | 90%（決済ぶん5% ＋ 運営5%） |

⚠️ 月のキーは **UTC**（ルールが `request.time` から作るため）。
日本時間では「毎月1日の午前9時に配られる」ことになる。
クライアント側も UTC で揃えてあるので、ずらすなら両方直すこと。

## 書誌データと表紙

外部APIを試した結果。

| | 結果 |
|---|---|
| **openBD**（ISBN引き） | ✓ 57ms・安定。**書誌はこれが正** |
| **国会図書館 SRU**（書名検索） | △ 動くが**1回20秒**、たまにタイムアウト。手元の道具だけで使う |
| 国会図書館 OpenSearch | ✗ 関連度で並ばない。「モモ」で1件目がイラスト辞典だった |
| **Google Books** | △ 鍵が要る。ページ数は取れる。**表紙はほぼ無い**（15冊中1冊） |
| **openBD の ONIX Extent** | ✓ ページ数。Google に無い日本の本を拾える |
| **国会図書館 `dc:extent`** | ✓ ページ数の最後の砦。`"308p ; 15cm"` の形 |
| 国会図書館の書影 | ✗ 画像はあるが**並列で叩くと返ってこない**。一次ソースにできない |
| **Amazon** | ✓ 表紙が確実に取れる。**ただし規約上グレー**（下記） |

### 表紙の優先順位

手で入れたもの → **Amazon**（リンクのある本だけ）→ Google（実在確認済み）→ 色の背表紙

⚠️⚠️ **Amazonの画像は規約上グレー。承知のうえで使っている。**
アソシエイト運営規約は商品画像を **PA-API 経由で取得すること**を求めており、
`images/P/{ASIN}` の直リンクは公式に認められた経路ではない。
少しでも趣旨に近づけるため、**Amazonリンクを設定した本にだけ**出している。
PA-API が取れたら（直近180日に3件の適格販売が条件）、そちらへ移すこと。
画像は保存していないので、URLの作り方を変えるだけで済む。

⚠️ **Google Books は、表紙が無くても `imageLinks` を返す。**
返ってくるのは「image not available」の絵で、15冊中8冊がまったく同じ画像だった。
**必ず中身を落として確かめること**（サイズ・重複・縦横比）。

⚠️⚠️ **Amazon も、表紙が無くても 200 を返す。**中身は43バイトの1×1で、
`onerror` は鳴らない。**読めたかどうかでは判定できない。**
`public/app.js` の `表紙をみる()` が、出たあとの `naturalWidth` で弾いている。

⚠️ ただし **`curl` で確かめてはいけない。**Amazon は相手を見て返すものを変える。
手元の `curl` に 43バイトが返ってきた本でも、ブラウザには本物の表紙が来た
（2026-09-23、『偉人たちの挑戦』6冊）。**判定はブラウザの中でやること。**

⚠️⚠️ **ISBN から作る URL（`/images/P/…`）が 1×1 でも、商品ページには表紙があることがある。**
Z会ペブル選書4冊は、ブラウザで見ても `/images/P/` は 1×1 だったが、商品ページの
`/images/I/51hi3M4yFxL.jpg` などに 345×500 の表紙があった（2026-09-23）。
このときは商品ページの `data-a-dynamic-image` から画像IDを拾い、**サイズ指定なしの URL**
（`_SY466_` などを付けない＝いちばん大きい元画像）を `coverManual` に入れる。
管理画面の「直す書影」と同じ欄。表示は `object-fit:cover` で枠に合わせるので、縮めて出る。

同じ日に棚の全冊を調べた。`/images/P/` で出なかったのは9冊（『パソコン入門』『三剣物語』4冊、
『クリス・クロス』『新世紀デジタル講義』『レプラコーンの涙』『アイディアファクトリー』）で、
**9冊とも商品ページに表紙があった。**持ち主が絵を見て確かめてから `coverManual` に入れた。
『知的生活』（Amazonリンクなし）も、`fetch('/dp/…')` の結果では「表紙なし」だったが、
**持ち主に指摘されて商品ページを実際に開くと、表紙があった**（`61IN1qu-uaL`、971×1337）。
`fetch` で取った HTML は、画面で開いたページと中身が違うことがある。
⚠️ 調べるのは**ブラウザの中で**（amazon.co.jp を開いたタブから `fetch('/dp/…')`）。
**「無い」と出たら、そのページを実際に開いて `#landingImage` を見てから結論を出す。**
取れた画像は**入れる前に絵を目で見る**こと。大きさだけでは別の本の絵を見分けられない。

### 団体の編者は、出版社と分ける

書誌の役割が「著」でない（ONIX の B01＝編）だけで落とすと、**受取人が消える。**

『偉人たちの挑戦』全6巻は「東京電機大学／編」で著者がいない。
出版社の東京電機大学出版局だけにすると、大学側が受取人から漏れる。
**同じグループでも、中の人が違う**ので分けた ―
東京電機大学は教授ら、東京電機大学出版局は編集者（2026-09-23 に判断）。

⚠️ 自動では判定しない。団体が編者のとき、それが出版社と同じ相手か別の相手かは、
書誌からは分からない（「編集部」なら同じ相手、「○○大学」なら別の相手）。
`Amazonリンクを入れる.mjs` は**著者が空の本を通すときに書誌の著者欄をそのまま出す**ので、
人が見て `著者を直す.mjs` の `直す表` に書く。

### 副題は必ず出す

『三剣物語』は1〜3巻と外伝で**題がまったく同じ**で、違うのは副題だけだった。
副題を出していなかったので、棚に同じ本が4冊並んで見えた（2026-09-23 に直した）。
`public/app.js` の `副()` を通すこと。題を出すところには必ず添える。

### 日本人の著者名が「名·姓」の順で入ることがある

Z会ペブル選書（増進会出版社）の4冊が、Google Books から「昭弘·野崎」の形で入った
（2026-09-23）。**このままだと届け先が `author:昭弘野崎` になり、同じ人が別の主体に割れる。**
名寄せでは拾えない（並びが違う別名として見える）ので、登録の出力に `·` が出ていたら
国会図書館で正しい表記を確かめ、`著者を直す.mjs` の `直す表` に書く。
出版社・刊行年が `null` で入るのもこの系統で、`欠けを埋める.mjs` が国会図書館から補った。

### ページ数の出どころは3つ

Google Books →（無ければ）openBD の ONIX Extent →（無ければ）国会図書館の `dc:extent`。

日本の本は Google に無いことが多い。**Google だけに頼ると欠ける**
（『偉人たちの挑戦』6冊のうち3冊が頁なしで入った）。
この3段にしたところ、頁なしが 26冊 → 3冊 になった。

## 本を増やす手順

⚠️ **この順に流すこと。**とくに「著者を直す」を飛ばすと、
翻訳書で訳者が著者（＝受取人）として登録されたままになる。

```bash
node 04_tools/Amazonリンクを入れる.mjs --新規 <URL>…   # 登録＋リンク
node 04_tools/著者を直す.mjs --下見 --掃除              # 表に足して確認
node 04_tools/著者を直す.mjs --掃除                    # 訳者を外す・ローマ字を直す
node 04_tools/欠けを埋める.mjs                         # 出版社・刊行年を補う
node 04_tools/名寄せを点検.mjs --ととのえる             # 名称の乱れを直す
node 04_tools/表紙をつける.mjs                         # ページ数・表紙
node 04_tools/在庫を入れる.mjs <判定.json>              # 品切れかどうか（下の「品切れを調べる」）
```

### 本のページの「この本について」（2026-09-26）

本の概要と読みたくなる紹介を**200字以内**で、書名・著者の下に出す（`books.intro`）。
- **Claude Code が書き、持ち主が確かめて直す**（管理画面の「直す」の「この本について」）。直して保存すると `checkedAt` が入り、
  `04_tools/紹介を入れる.mjs` で上書きされなくなる。見出しは「この本について」だけ（持ち主の判断）
- ⚠️⚠️ **確かめた出どころに基づいて書く。**探す順：openBD の内容紹介 → Google Books → 出版社・書店 → ブクログ・読書メーター。
  それでも無ければ**保留**（紹介なし）にし、持ち主が本を探して書く。出どころの文は写さず自分の言葉で。結末に触れない。
  広く知られた作品（モモ・1984 など）は、よく知られた筋立ての範囲で補い、出どころにそう書く
- 本を増やすとき・申請を処理するときも、最後に紹介を書く
- 初回：92冊中87冊。保留の5冊（『宇宙論講義』『英語で読む 1』『サンドリヨン』『三剣物語 2』『三剣物語 外伝』）は、
  持ち主が都立図書館・図書館の蔵書目録・国会図書館の内容細目・当時の生協の紹介記事などを掘り起こし、それをもとに書いた。
  これで全92冊。『サンドリヨン』は収録作のうち**確かめられたものだけ**を挙げた（推測した作品は書かない）。
  下書きと出どころは `99_notes/紹介_2026-09-26.json` と `99_notes/紹介_保留5冊_2026-09-26.json`

### 申請を処理する（案B。2026-09-26 決定）

利用者からの申請は、持ち主が「申請を処理して」と Claude Code に頼み、**持ち主は登録するか否かだけを決める。**
確認と後続の処理は Claude Code が下の順で流す（管理画面を自動化する案Aは見送った）。

1. `node 04_tools/申請.mjs` で未処理の申請を並べる。**同じ ISBN・題の似た本が棚にあれば ⚠ が出る**
   （『感情労働の未来』は、管理画面から並べ済みだった）
2. 書誌を確かめる：openBD → Google Books → 国会図書館（`isbn=`）→ Amazon の商品ページ（ブラウザで）
3. 著者の役割を国会図書館の `<author>` で確かめ、「届け先は著者だけ」のルールで決める。
   海外の著者は読者が知っている表記（『サンドリヨン』は C.ペロー → シャルル・ペロー）
4. **持ち主に、登録するか見送るかを聞く。**⚠ が出た本・判断が要る本は、理由を添えて
   ⚠️ **棚にある作品の別の版（文庫・単行本など）なら、新しい本にしない。**「版として足す」を持ち主に提案する（下の「版」の節）
5. 登録するなら「本を増やす手順」の道具で並べる。書誌が無い本は `1冊を登録.mjs` に `--題 --著者 --出版社` で渡し、
   年・ページ数はあとで補う。
   別の版なら `node 04_tools/版を足す.mjs --下見 <作品のISBN> <版のISBN か AmazonのURL> --版 文庫`
   で確かめてから、`--下見` を外して書く
6. 品切れを調べる（下の節。ブラウザで）→ `在庫を入れる.mjs`
7. **`node 04_tools/申請.mjs 並べた <申請id> <ISBN>`**（見送りなら `見送り <申請id>`）。
   別の版として足したなら、版の ISBN を渡せばよい（行き先は作品のページになる）。
   ⚠️ これを忘れると、申請した人のマイページに「棚に並びました」が出ず、「棚に加えた本」にも数えられない
   （管理画面の「本にする」はこれを自動でやっていたが、手元の道具はやらない）
8. 本番の本のページで確かめてから報告する

### 品切れを調べる（2026-09-24 から。**月に1回、全冊を調べ直す**）

「復刊を願う」は品切れの本にだけ出る。品切れかどうかは **Amazon の商品ページ**で判定する。
- openBD の販売状況（`ProductAvailability`）は全冊「99＝不明」で使えなかった。国会図書館は販売状況を持たない
- ⚠️ 判定は**ブラウザの中で**やる（Node の fetch や curl には Amazon が別の中身を返す）。
  amazon.co.jp を開いたタブから `fetch('/dp/<ASIN>')` して、次の決まりで分ける。1冊ごとに1秒ほど空ける
  - 新品の購入欄（`#newAccordionRow` など）があり、販売元（`#merchantInfoFeature_feature_div`）が Amazon.co.jp → **流通**
  - 新品の購入欄が無く、中古の欄（`#usedAccordionRow` など）だけ → **品切れ**
  - 新品を売っているのが書店・古書店だけ → **要確認**（流通のまま。人が決める）
  - 新品も中古も出品が1つも無い → **出品なし**（品切れと同じく `status:"絶版"`。2026-09-26、『サンドリヨン』1980年で足した）
- 結果を `{ "<ASIN>": ["流通"|"品切れ"|"要確認", "題"] }` の JSON にして `在庫を入れる.mjs` で書く。
  判定の日（`statusCheckedAt`）と根拠（`statusNote`）が本に残り、本のページに「（Amazon で新品なし・9月24日時点）」と出る
- ⚠️ **「Amazon に新品が無い」は「絶版」ではなく「品切れ」。**画面では「品切れ」と書き、言い切らない。
  中の値は `status:"絶版"` のまま（名前を変えると古い記録と食い違うので）
- ⚠️ 管理画面で状態を手で変えた本は `statusNote:"管理者が設定"` になり、自動の判定では上書きしない
- ⚠️ **別の版（`editions`）の ASIN も調べる。**`在庫を入れる.mjs` は版ごとに書き込む。
  作品が「品切れ」と出るのは**全部の版が品切れのとき**だけ
- ⚠️ 規約上は、表紙の画像と同じくグレー。楽天ブックスの API（アプリIDが要る）に移す道がある
- 初回（2026-09-24）：流通 54 ／ 品切れ 26 ／ 要確認 9。判定のファイルは `99_notes/在庫判定_2026-09-24.json`。
  見立てどおりだった（『二十歳のころ』は出版社が2010年に解散済み、など）

## 引っかかりやすいところ

- **`node --check` を通しても足りない。**インラインの `onclick` などは
  **グローバルスコープで動く**ので、`type="module"` の中の変数は見えない。
  値を入れるものは必ず `window` に出した関数を通すこと（ことばを取りこぼした実績あり）
- ⚠️⚠️ **onclick などに値を渡すときは、必ず `引数()` を通す**（`共通.js`）。
  `逃()` では守れない。属性の中の `&#39;` は HTML が `'` に戻してから JS に渡すので、
  `onclick="go('books',{q:'${逃(q)}'})"` は、`?q='+(任意のコード)+'` の URL を踏ませるだけで
  **何でも動かせた**（並び順の `?s=` は逃がしてすらいなかった）。2026-09-23 に本番で再現を確かめてから塞いだ。
  書き方は `onclick="go('book',{id:${引数(b.id)}})"`（外側に `'` を付けない）
- ⚠️ **戻ったときのスクロール位置は、自分で覚えて戻している**（`app.js` の「戻ったときに、元の位置へ」）。
  ブラウザ任せだと、描き直しの途中でページが短くなるので、一覧から本へ行って戻ると一番上に戻っていた。
  位置は移る前とスクロールが止まるたびに `history.state.y` に書き、戻ったら**描く前に読んで、描いたあとで**戻す。
  確認するときの注意：ブラウザ欄が隠れていると `scroll` の知らせが出ない（`document.hidden`）
- ⚠️ **利用者が書く値を、`style` にそのまま入れない。**しるしの色が `style="background:${色}"` に
  入っていて、ルールは長さ（16文字以内）しか見ていなかった。`"onclick=ログアウト()` がちょうど16文字で、
  **他人の画面で動いた。**いまは画面とルールの両方で `#` と16進6桁だけにしている
- **お金の計算は `共通.js` の `受取人へ` / `額の内訳` / `内訳を作る` だけでする。**
  前は窓の表示と控えの集計が別々に掛け算していて、同じ本返しの受取額が1pt ずれた。
  `受取率` は `1-0.05-0.05`（＝0.8999…）ではなく、百分率で丸めた 0.9 ちょうどにしてある
  （そうしないと 25pt の9割が 23 → 22 に変わり、過去の記録まで変わって見える）
- **`new RegExp(\`…\`)` の中で `[\s\S]` と書かない。**テンプレート文字列が `\s` を `s` に
  潰して `[sS]` になる。`[^]` を使う
- **Node の `fetch`（undici）は国会図書館に 429 で弾かれる。**curl なら通る
- **Firebase Hosting の既定は `max-age=3600`。**SPA なので index.html を1時間掴まれると
  直したものが届かない。いまは全ファイル `no-cache` にしてある

## 決めたこと・保留していること

### 著者は届け先に残す。ただし実決済では Claim 済みにしか払い出さない（2026-09-23 決定）

「MVPは出版社だけに絞るべきでは」という検討をした。出版社は数が限られ（JPRO 約3,000社）、
日本の法人で、登記で本人確認ができ、複数タイトルを束ねられる。
著者は数が多く、海外の場合があり、亡くなっていることもある。

**実際、棚の著者18人のうち、ダンテ（1321年没・伊）、P.G.ハマトン（1894年没・英）、
立花隆（2021年没）、石田晴久（2009年没）、オーウェル（1950年没・英）、
サリンジャー（2010年没・米）、シェイクスピア（1616年没・英）が故人。**
懸念は仮説ではなく、目の前で起きている。

それでも**著者を外さない。**理由は3つ。

1. **配分の選択そのものが、測りたいデータ。**「著者70%・出版社30%」という選択は、
   読者が誰に感謝しているかの表明。出版社だけにすると、この情報が丸ごと消える
2. **出版社が消えている本では、著者しか残らない。**ランダムハウス講談社（2010年解散）の
   『二十歳のころ』がそれ。絶版本こそ読者の思いが濃い、というのが出発点だった
3. **読者の気持ちは、まず著者に向く。**UIから消すと、動機と画面がずれる

### 主体の状態は3つ（実決済に移すときに実装）

⚠️ **「故人かどうか」はシステムで判定しない。**著作権は死後70年続き、継承者が
Claim する可能性がある。生死の判定という厄介な仕事をまるごと避けるため、
基準は **Claim されているか一本**にする。ダンテもハマトンも「未Claim」なだけ。

| 状態 | 配分先に出すか | お金 | 気持ち |
|---|---|---|---|
| 未Claim | 選べない | 払い出さない | **記録できる** |
| Claim済み | 選べる | 払い出す | 記録できる |
| 辞退 | 出さない | — | 記録もしない |

⚠️⚠️ **未Claim の主体には「貯めておく」ことをしない。**
受け取る人がいないお金を預かることになり、
**「絶版本では1円も預からない」という原則**に正面から反する。資金決済法の論点もそこから出る。

そのかわり、**お金は Claim 済みにだけ、気持ちは未Claim にも。**
品切れの本の「復刊を願う」とまったく同じ仕組みで、
「この著者にも返したかった」という意思だけを貯める。
復刊交渉・権利者探し・出版社を口説く材料になる。

> 『神曲』に100pt返す → 配分先は講談社のみ（ダンテは未Claim）
> → 「ダンテにも返したかった」にチェック → ダンテのページに意思が貯まる

**いまはトライアル中なので、未Claim にも配分できる今の形のままでよい**
（架空のポイントなので実害がない）。切り替えるのは実決済に移すとき。

### ビジネス上、最初に口説く相手は出版社

プロダクトから著者を消す必要はないが、**Claim を呼びかける相手は出版社から。**
法人で本人確認ができ、複数タイトルを束ねられるのでスケールする。
著者は「存命かつ本人が乗り気な人」を数人。故人・海外著者は当面 Claim されない前提でよい。

### 届け先にするのは「著者」だけ（2026-09-25 決定・MVP の方針）

- 届け先にするのは、国会図書館の書誌で**「著」「作」「文」**の人だけ
- **原作・原案・監修・訳・絵・写真**と、「著」がいる本の**「編」**は、登録も表示もしない（届け先にできない）
- **「著」がいなくて「編」だけの本は、編者を著者とする**（『偉人たちの挑戦』→ 東京電機大学）。
  ただし編者が出版社そのもののときは、著者を置かず出版社だけ（『立花隆のすべて』＝文藝春秋 編）
- 役割は国会図書館 OpenSearch の `isbn=` の `<author>` で確かめる（「Ado 原作,小松成美 著」の形で付いている）。
  直すのは `著者を直す.mjs` の表。著者欄の書き方を変えたいときは `{ 名ら:[…], 表示:"…" }`
- 例外：『二十歳のころ』は「立花隆, 東京大学教養学部立花隆ゼミ 著」だが、ゼミは受け取る相手として
  実在しないので立花隆だけ（持ち主の判断）

2026-09-25 に全89冊を照らし合わせて直したのは3冊：『ビバリウム』（Ado 原作を外し小松成美だけ）、
『レプラコーンの涙』（編の安田均を外し水野良だけ）、『立花隆のすべて』（立花隆について書かれた本で、
書き手ではない。文藝春秋 編なので出版社だけ）。訳者・絵の人は前から外してあった。
⚠️ **過去の本返しの記録は書き換えない。**『レプラコーンの涙』への本返しは安田均にも配られていて、記録に残る。
外れた相手（Ado・安田均）の主体は消した（番付に出なくなる）。消す前の中身は `99_notes/消した主体_2026-09-25.json`。

### 翻訳者は、いまは届け先にしない（2026-09-23 決定）

原著者と出版社だけ。翻訳書では訳者の寄与が大きい（『知的生活』の渡部昇一、
『モモ』の大島かおり、『夜と霧』の池田香代子）が、**将来的に検討**とした。

⚠️ あとから足しても、**それ以前の本返しには反映されない。**
入れるなら早いほうが楽、ということだけ承知のうえでの保留。

### 吸収された出版社は、分けたまま（2026-09-23 決定）

メディアワークス・富士見書房は、いまはどちらも KADOKAWA だが、**分けて持つ。**
レーベルごとに編集部が違い、**中の人が違う**ため
（東京電機大学と東京電機大学出版局を分けたのと同じ理由）。

⚠️ ただし **角川書店 → KADOKAWA だけは統合済み。**あちらは吸収ではなく社名変更で、
同じ相手の別表記だから。登録するとき `--出版社 "角川書店"` と書くと
**統合した主体が復活する。**KADOKAWA と書くこと。

⚠️ 実際に配分するときは、受け取れる法人が KADOKAWA だけ、という事態がありうる。
そのときは主体に「受け取りは誰へ」を持たせる必要がある。いまは考えない。

### トップの「ありがとうが集まっている本」の列は外した（2026-09-23 決定）

すぐ上の番付「いま、推されているもの」（本・著者・出版社）と中身が重なるため。
返しのある本が少ないうちは、同じ本が繰り返し流れて見えてもいた。
トップの流れる列は「新しく入った本」だけ。金額順で全部見たいときは、本の一覧の並べ替えを使う。

### 本返しの金額は、いまのまま（2026-09-23 確認）

### いまの気分で選ぶ（2026-09-26 決定）

マイページに「いまの気分で選ぶ」。気分を書くと、AI が**棚の本から3冊**選んで理由を添える。

- **棚の本だけ。**棚に無い本を薦めても本返しできない。返ってきた ISBN は処理の側で候補にあるか確かめ、
  無いものは捨てる（AI に ISBN を作らせない）
- もう本返し・ことばを書いた本と、復刊を願った本は候補から外す（次に読む本を薦めたい）。足りなければ棚ぜんぶ

- 気分と記録の中身は**ログに出さない**（その人の内面なので）。出すのはトークン数だけ
- 「しくみ」の「届け先と、記録の扱い」に、OpenAI へ送ることを書いた
- ⚠️ 鍵は GEMu_Web と同じ名前 `OPENAI_API_KEY` で Secret Manager に置く。**プロジェクトが別なので、登録も別。**

### 将来の構想：ことばを AI で評価する

一定の基準（具体性・その本でなければ書けないか・読んだ時期や状況があるか など）で、
Claude API にことばを採点させる案。
- **作りの方針を崩さないやり方がある。**Cloud Functions ではなく手元の道具（`04_tools`）でまとめて採点し、
  管理者しか書けない場所に点数を置く
- **点数を見せるかは慎重に。**点数が付くと書くのをためらう人が出る（賭けどころは「ことばを書くか」）。
  はじめは運営の内側だけで使い、出版社へ「質の高い声」を渡す材料にする
